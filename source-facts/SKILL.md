# 源码事实提取

> Author: chenhh

围绕用户指定的范围，查清当前代码实际怎么运行，并输出可供另一位开发人员或后续 Skill 使用的事实包。不要把事实提取扩展成实现、重构或整个工程的审查。

## 输入与工作边界

从请求和上下文确定工程、目标节点 / 模块 / 机制、需要追踪的入口与结束边界；接受自然语言，不要求固定参数格式。范围不能明确时先澄清，不自行选择另一段代码。

设计、实现状态、开发计划、测试与运行日志是可选的辅助材料。按工程现有约定寻找相关资料，不要求固定文件名、目录、语言或框架；没有某类资料不妨碍提取可确认的源码事实。

默认只读取、分析并在对话中输出事实包。用户要求保存时，可写入指定或上下文已明确的事实包文件；不因此获得修改源码、设计或计划、执行构建与运行测试的授权。

## 提取方法

1. 先读取适用的工程约束。遵守工程的检索工具与优先级，使用索引或符号检索定位，只展开目标范围必要的源码；工具不可用时使用允许的替代方式，不为分析自动安装工具或改配置。
2. 查清真实路径：入口、关键先后顺序、调用、回调或异步交接、改变语义的分支与早退、正常及失败的结束边界。区分“调用”“数据传递”“先后发生”，不要用一种箭头混淆它们。
3. 查清关键对象：实际保存哪些数据或控制什么状态，谁创建、谁拥有、谁写、谁读；是拥有、借用、临时结果、快照还是队列项，何时有效、何时失效。不保存业务数据的对象，要说明它实际检查或限制什么。
4. 查清数据与存储：代表性数据放在哪里，谁分配和填充、谁消费，是否另有底层存储，何时清空、复用、转交或回收；复制、移动和借用分别有什么语义，容量或分配失败怎样处理。
5. 查清状态和版本：如存在状态机、generation、revision、epoch 等，分别追踪维护者、保护对象、变化条件、比较位置、过期后的行为与下一次如何重新开始；不要把不同计数合并成一个“版本号”。
6. 查清并发和交接：哪些操作允许在哪个线程或执行上下文发生，哪些状态独占或共享、哪些输入只读，任务结果在哪里被接纳、归并或发布；跨线程、异步及跨调用的引用靠什么存活。
7. 查清失败与收尾：异常、取消、无效身份、局部拒绝和整体失败分别怎样处理；自动收尾、回滚、延迟回收是否仍执行，哪些状态只有真正成功或越过提交点后才生效。
8. 如有明确目标设计，再对照实现。设计资料说明目标，源码说明实现，计划只用于定位已确认差距；没有设计或证据不足时写“无法确认是否对齐”，不能把资料缺失判断为实现缺陷。

上述问题按实际机制展开；不存在并发、显式内存管理或版本检查时说明不适用，不强行补出这些机制。

## 事实包约定

用 Markdown 按以下主题组织，保留影响后续解释的事实。简单机制可合并重复内容；不适用的主题说明原因，未确认的主题保留缺口。

| 主题 | 应交付的内容 |
|---|---|
| A. 范围与依据 | 分析对象、入口、结束边界、不展开的范围；已读源码与辅助资料，影响结论的版本或配置条件 |
| B. 核心事实 | 关键行为与当前源码锚点；区分已确认事实、推断和未确认内容 |
| C. 真实路径 | 主流程及改变行为的分支；标清调用、数据流、异步交接和先后关系 |
| D. 关键对象 | 实际数据 / 控制状态、创建者、所有者、写者、读者、有效期 / 失效点及源码位置 |
| E. 数据与内存 | 存什么、在哪里分配和填充、谁使用、何时转交 / 复用 / 回收、失败语义 |
| F. 生命周期与状态 | 进入前状态、创建 / 准备、使用、状态切换、收尾、下一次开始；版本变化和过期检查标在对应位置 |
| G. 分支、失败与收尾 | 早退、局部失败、异常、取消、回滚和自动收尾；失败后仍要执行的工作及成功后才能生效的状态 |
| H. 易混概念 | 当前机制中相似名字或状态实际有什么区别 |
| I. 目标对照 | 如有目标，说明对齐 / 部分对齐 / 不对齐及依据；差距对应的计划条目，未找到时明确说明；未提供目标或计划时分别注明 |
| J. 调试观察 | 少量高价值断点或观察位置、为什么看这里、关键值和预期变化；预期不写成已经验证的运行结果 |
| K. 未确认与验证范围 | 证据缺口、影响哪些结论、实际采用的核验方式；没有未确认项才写“无” |

D 可用对象事实表，C / F 可用文本图或工程支持的图示。形式服务于事实，不输出完整 API 清单或大段源码。

## 事实可靠性

- 每个关键结论给出可回查的路径与符号，必要时加行号。索引或调用图只作定位线索；对影响结论的间接调用、条件编译、宏、模板、注册分派等，回到相关源码核实，不能确认就标明。
- 不根据类名、字段名、常见架构或目标文档猜当前行为；不把未来方案、示例或测试断言当成已运行通过的实现。
- 源码阅读、测试定义、实际执行结果各自只能支持对应层级的结论；运行日志还要考虑版本、配置和场景，不与不同条件下的源码直接混为一谈。
- 资料冲突时指出具体冲突与证据条件，优先核对当前源码和相匹配的运行结果。说明“为什么这样设计”若只能从约束推得，明确写为推断，不编造作者动机。
- 资料不可访问或路径无法追清时，写“当前无法从已读材料确认”及具体缺口，继续完成不受影响的部分；目标源码完全不可访问时报告无法提取，不伪造事实包。
