# 基于源码事实的工程导读

> Author: chenhh

读者有一定软件开发基础，但第一次接触该工程。目标是让他们轻松读懂这一段代码在工程中做什么、怎样运行，知道改代码从哪里下手，以及哪些条件不能破坏。

尽量用大白话，保留准确含义。正文帮助建立直觉，源码名帮助定位，细节支持实际修改；不要把上游事实包原样铺成一篇术语密集的报告。

## 输入与上游接力

- 上游材料是 [source-facts](../source-facts/SKILL.md) 的事实包，可以来自对话或文件；不要求特定存储格式。
- 从请求和上下文确定导读范围、已有文档、目标文件或目录。没有文件写入请求时在对话中输出；要求创建或同步文档时，直接更新已明确的目标。
- 已有事实包先复用，不重新分析全部源码。若缺失、关键事实不完整或源码已变化，先按 source-facts 在本轮范围内补齐或更新，再展开导读；只需确认少量锚点时，不重做整份事实包。
- 范围仍不明确或关键行为无法确认时，先澄清或保留具体缺口；可以完成有依据的部分，不能用故事补上未知流程。
- 这一步整理和写文档，不自动修复源码、改设计或扩展开发计划。新增代码分析遵守工程约束与 source-facts 的工作边界。

## 从事实写成导读

### 先让读者知道自己在哪里

开头先用自然语言说明本节要解决的问题、它在整体流程中的位置、进入前已有些什么、到哪里算结束，不从内部类名或函数清单开始。必要时链接相邻章节。已有节点编号和导航就沿用，没有就用范围说明，不编造一套编号或阶段。

### 先用比方，再讲机制

从事实包支持的场景选一个贯穿例子，先讲“谁拿到什么、做了什么、交给谁”，再对应源码。阐述关键设计时，先用生活示例、物理规律或读者熟悉的计算机机制建立直觉，再解释工程中的真实机制；同一流程尽量沿用同一个比方，不为每个函数另造故事。

说明比方与代码各部分的对应关系，以及容易误解的边界；比方不能代替真实的时序、状态或所有权说明。假设输入标为例子，不把它写成已经验证的真实运行。

对于关键的职责拆分、顺序、异步或生命周期安排，讲清“实际问题 → 怎样处理 → 为什么有效 → 不这样做会出什么问题”的因果关系，不能只列调用步骤或说“为了安全 / 性能”。依据是代码事实与已确认约束；不能确认的设计动机写成推断，不补历史故事。

### 先说作用，再给名字

只介绍理解或定位当前章节必需的代码名。所有出现的功能性代码名，包括模块、类型、函数、阶段和状态字段，都要在首次出现时用人话解释它实际做什么、保存什么或检查什么；该要求同样适用于标题、图示、表格和代码示例。解释可写在句中或紧邻的名字对照表中，不能只依赖文末术语表。

几个相似名字应说明各自职责及区别，不要用陌生术语解释另一个陌生术语，不连续堆缩写。该保留的精确名称仍保留，便于搜索源码；不为通俗而把不同对象、状态或版本号叫成同一个东西。

### 正文先走主流程，再展开细节

正文从宏观到微观：先整体目标与职责关系，再主要阶段和交接，最后局部对象、函数、字段与实现细节。导读范围只涉及一个局部机制时，也先交代它在上层流程中的作用，不扩写无关架构。

读者不展开细节也能理解主流程和关键限制。可按“整体定位 → 例子 / 比方 → 原理与因果 → 主流程 → 局部细节 → 当前边界 → 改代码与调试”组织，不强制固定小节数；已有符合要求的结构直接沿用。

用短段落和具体动词讲步骤；图示适合表现先后、分支、交接和状态，表格适合比较职责或映射源码。使用目标文档能呈现的文本图、Mermaid 或其他现有形式，不为一篇导读增加阅读环境。

分支、早退、失败收尾、线程限制和有效期若改变主流程，正文必须指出。字段、完整失败矩阵、版本检查、内存明细等可放进折叠区或后续细节，但不能删掉；格式不支持折叠时用清楚的小节或链接。

如实区分“准备好”“已交出 / 已提交”“已完成”“已发布”；明确数据是拥有还是借用、操作在什么上下文发生、失败后还有哪些收尾，避免比方掩盖真正的边界。

### 让读者能找到修改位置

给出少量高价值源码入口，解释为什么从这里下手；可用“想改什么 | 看哪个文件 / 符号 | 必须保住的规则”表。

根据当前机制指出修改时需要保持的职责、调用顺序、所有权、状态、线程与失败语义，不设计一套未经请求的新实现。源码链接沿用工程约定，名称必须能在当前源码中找到。

调试部分挑少量断点或观察位置，说明看哪些值、前后应如何变化、什么现象说明走了另一个分支。未经执行只写调试建议和预期，不宣称验证通过，也不自动启动程序。

### 当前事实、目标和未知分别写清

已实现能力、尚未完成的能力、尚未验证的行为分别说明，不能互相替代。目标对照和计划映射来自事实包；没有对应设计或计划就注明，不臆造路线。

## 同步已有导读

用户要求同步改动时，先用本轮事实包找受影响的章节、总览、术语、调用图、源码入口和链接，只更新有变化的部分，不无关重写。

当前流程直接写当前事实，清理对应的旧入口和过期状态。文件改名时同步引用；跳过、失败或异步路径不能因为主流程变化而被漏掉。保持相邻章节的词义、例子和边界一致，避免一个机制出现两套解释。

## 完成前复核

- **读得懂：** 内容按整体、阶段、局部逐层展开；不熟悉工程的开发人员能说出本节作用、主流程、关键分支和修改入口，正文不依赖折叠区才能明白基本意思。
- **讲清机制：** 关键设计先有易懂的比方，再有真实机制、为什么有效及不这样做的具体后果；设计动机的推断已标明。
- **名字有解释：** 逐项检查标题、正文、图示、表格和代码示例中的功能性代码名，首次出现都有就近解释，相似名字的职责区别清楚。
- **事实不走样：** 对照上游核对顺序、条件、状态、拥有 / 借用、线程、版本与失败收尾；比方、图示和正文没有与事实包冲突，未知仍标为未知。
- **能回到源码：** 关键入口与符号有效，修改约束和调试预期有依据。
- **文档一致：** 核对相关导航、术语、图示、链接、折叠或代码块，以及工程要求的文档检查；没有实际执行的检查不报通过。

文件写入后，简要说明更新范围、主要变化、实际检查及仍未确认项；对话输出导读时，直接给出导读本身。
